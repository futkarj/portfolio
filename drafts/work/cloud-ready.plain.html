Cloud-Ready AEM Without a Cloud Sandbox

TL;DR: Most AEMaaCS deals start on 6.5. I show how to assess and modernize a 6.x codebase for Cloud Service entirely locally, and how to tell that story to a buyer worried about migration cost.

Why this demo: I've run this conversation for real. At Adobe I advised 100+ enterprise AEM customers on upgrades and cloud adoption, and at Capgemini I shaped the Cloud Service migration roadmap for a financial services client. This demo turns that advisory motion into something a buyer can watch.

The buyer problem

  • "We're on 6.5 and dread the next upgrade."
  • "We don't know how much of our code will break on Cloud Service."
  • "What does 'evergreen' actually mean for our team?"

What I'm building (all local, in progress)

Status (Oct 2026): the Cloud target runs on the local AEMaaCS SDK, and its Dispatcher config passes all three validator checks. The AEM 6.5 LTS baseline (15 deliberate legacy patterns) is assessed from its code. Modernizing the flagged patterns is next.

  1. Baseline: a sample AEM 6.5 LTS project with some deliberately "legacy" patterns (static templates, custom replication agent, /apps content, a non-immutable config).
  2. Assess: from the code alone, with no running 6.5 LTS instance: Adobe's open-source AEM agent skills (migration runbook, code assessment), the Cloud Manager build analysers, and the Dispatcher Converter. On a real engagement, the Best Practices Analyzer on the customer's instance adds the repository-level findings. Everything comes from my sample project, not customer data.
  3. Modernize: regenerate the project with the AEM Project Archetype targeting Cloud, then refactor the patterns the assessment flagged (and the AEM Modernize Tools for static → editable templates).
  4. Validate: build with the Cloud Manager build analysers, deploy to the AEMaaCS SDK quickstart, and run the Dispatcher validator, all locally.

Code: https://github.com/futkarj/aem-cloud-readiness-demo

What I found so far

  • The tools caught 7 of my 15 planted patterns. They are strong on Java blockers (replication, asset uploads, JCR listeners) and weak on repository-level ones (content in /apps, configs, Classic UI dialogs). That gap is why BPA still matters on a real instance.
  • The Cloud Manager build analysers pass on the legacy code. A green build is not the same as cloud-ready: admin logins and replication agents compile fine and fail at runtime.
  • The Dispatcher Converter silently dropped the site's 19 publish filter rules. A verification step caught it before anything shipped. Automated conversion saves time, but the output needs expert review.

Full write-up: https://github.com/futkarj/aem-cloud-readiness-demo/blob/main/docs/assessment/README.md

Demo flow (8 minutes)

  1. Hook (1 min): "Here's what your next upgrade looks like on 6.x vs. on Cloud Service: zero."
  2. Readiness report (3 min): walk through the findings by category, show what local tools catch and what needs BPA, and turn them into an effort estimate.
  3. Before/after code (2 min): show the diff side by side, e.g. a static template turned into an editable one, or OSGi config moved to run-mode folders.
  4. Pipeline story (2 min): show that the build analysers pass on the legacy code, then explain what Cloud Manager's quality gates do and don't catch. A diagram is fine here, since there's no sandbox.

Discovery questions

  • When was your last AEM upgrade, and what did it cost in time?
  • How many custom OSGi services / replication customizations do you have?
  • Who owns Dispatcher config today?

Objections & answers

  • "Migration is too risky." → Scope the work with a code assessment now and BPA on their instance, and show the Cloud Acceleration Manager as the guided path.
  • "We lose control on Cloud." → Explain what stays yours (code, Dispatcher config, pipelines) vs. what Adobe runs.

What's next
